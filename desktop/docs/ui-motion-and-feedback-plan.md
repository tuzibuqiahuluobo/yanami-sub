# UI 状态反馈与动效优化计划

记录日期：2026-11-03。实施日期：2026-11-04。状态：功能修复与公共控件动效已实施，待发布。

此文保留原始方案和验收要求，末尾记录实施与测试结果。以下编号是本地跟踪编号，不是 GitHub Issue 编号；本次未推送或发布版本。

## 1. 目标与边界

核心目标是让用户始终知道三件事：**操作是否已接受、当前正在做什么、遇到问题该去哪里处理**。先修复状态与引导，再完善动效。

- 保留 Yanami Sub 的现有明暗/角色主题、字体、卡片布局与图标体系，不照搬参考项目的外观。
- 参考用户提供的 ChatLuna 分析中的状态驱动、统一缓动、退场生命周期等思路；未独立审计该项目，也不把其 Base UI、Tailwind 或 tw-animate-css 当作本项目依赖。
- 优先复用现有 React 状态、CSS、CustomSelect、ConfirmDialog、ToastProvider 和原生 View Transitions；本轮方案不要求新增动画库或整体更换组件库。
- 新建任务、批处理开始、批次继续及运行中追加链接使用一致的前置条件与提示规则；实际必需资源仍由后端按具体请求判定。
- 动画不得延迟任务提交、改变任务调度、触发下载或模型调用。是否允许安装/启动继续遵循现有确认与权限边界。

## 2. Bug 与新增需求登记

### BUG-UI-001：首页资源按钮下载中仍显示下载箭头

优先级：P2，状态反馈缺陷。

用户现象：新建任务页右侧运行环境面板点击下载后，右侧仍显示下载按钮，而不是正在下载的圈圈。实际资源操作正常，结束后能正常显示已安装。截图页脚为 0.2.1.post1；截图本身不足以判断后台正在下载、安装依赖还是校验。

源码证据：EnvironmentPanel 已根据 `resource.state === "downloading"` 判断忙碌，左侧会显示 LoaderCircle，但右侧按钮始终渲染 Download；`disabled={busy || isBusy}` 只禁用操作，不改变图标。这是已确认的显示逻辑问题，不等同于实际下载失败。

拟修复：

1. 点击后立即进入提交/准备状态，右侧替换为圈圈，屏蔽重复点击；不能等第一次轮询才反馈。
2. 在首页、资源页和侧栏复用同一份资源安装快照/状态判定。保留排队、下载、校验、安装、暂停、失败与就绪的不同含义。
3. 有可靠字节进度时显示环形进度；未知总量、排队和安装时显示不确定圈圈及实际阶段文案。不能根据准备时间编造百分比。
4. 成功仅在后端确认可用后显示对勾；暂停提供继续入口，失败提供重试和真实错误。动效关闭时保留静态进度与文字。
5. 检查 `resourceInstallChanged` 后紧跟 `resourcesLoaded` 的覆盖顺序：旧资源状态不能让正在运行的安装短暂退回下载箭头，也不能让旧安装记录覆盖新一轮重试。按活动安装/代次识别，不靠固定延时硬撑。

验收：Python/FFmpeg 等资源的请求刚发出、排队、下载、安装、暂停、失败重试和成功阶段均正确；切页再返回一致；快速连点只创建一个有效安装；完成显示已安装的既有正常行为不回退。

### BUG-BATCH-001：添加链接后开始批处理，无提示跳到设置且不执行

优先级：P1，任务开始阻塞且原因不可见。

用户现象：在批处理里添加链接并点击开始后，跳到设置页，没有提示，也没有开始批处理。本次没有对应 URL、错误码或日志，尚未确认其具体缺少哪项条件。

源码已确认的相关问题：

- BatchQueue.start 遇到 `api_key_required`、`open_agents`、`open_settings` 时先跳转设置，再把错误写入批处理组件的局部状态。原错误条只显示在批处理页；跳转后自然不可见。
- 批处理草稿列表、链接输入与并发配置主要存在组件局部状态里。切到设置后组件卸载，尚未启动/落盘的草稿可能丢失。
- 后端 start_batch 先检查模型配置，再检查资源，因此同一个任务同时缺模型配置与下载组件时，先收到设置类错误是可能的。不能把此次跳转直接断言为 yt-dlp 缺失。

拟修复：

1. 把启动失败原因与来源任务保存在应用级引导状态，目标页显示持续可见的说明，不只依赖短暂 Toast。
2. 跳转必须携带明确目标：缺免费 API 密钥定位到该密钥输入；Agent 问题定位到就绪/登录入口；路由问题定位到对应路由项；缺资源则定位资源卡片，不能统一送去设置。
3. 将未提交的批处理草稿提升到应用级内存状态，保留链接、顺序、模型选择、并发及其他参数。默认不为此永久保存用户的私有链接。
4. 在目标页提供“返回批处理继续”入口，条件就绪后由用户明确点击重新开始。避免配置一保存就悄悄触发付费调用，避免重复创建批次。
5. 同时补齐新建任务与运行中追加链接的同类错误路径：不能只修开始批处理这一处。
6. 无法识别的错误保留原文、错误码与可用日志入口，停留在当前任务上下文；不能静默跳页或假装批次已开始。

验收：分别覆盖缺密钥、Agent 不可用、路由无候选、缺 yt-dlp、缺 Python/FFmpeg、无效链接与桥接异常。每次均说明原因、定位正确、草稿不丢；全部前置条件满足时应正常产生一个批次，而不是只完成跳转。

### UX-RESOURCE-001：缺少资源时精确定位并持续黄色高亮

优先级：P1，与上述启动引导一起实施。

用户要求：例如链接任务尚未安装 yt-dlp，自动打开对应界面，并一直黄色高亮提醒下载。

现状：ResourceManager 已有 `resource-<id>` 锚点及一次性的滚动/聚焦，但没有“本次任务仍需要此资源”的持续高亮状态。批处理的资源入口还会用全局必需资源第一项或 uv 兜底，无法保证定位到只对链接任务必需的 yt-dlp。

拟实现的交互：

1. 用户明确点击开始/继续/追加后，若后端报告缺少必要组件，自动进入资源页并定位到真正缺少的卡片，而非笼统切换页面。
2. 卡片持续显示淡黄色底、黄色边框和“此任务必需”标记，附具体原因。例如：“此批次包含视频链接，需要 yt-dlp 下载媒体。”使用主题化警告色，不持续闪烁、不靠颜色单独传意。
3. 多项缺失显示清单，优先定位依赖链最前面的可操作项，例如 Python 未就绪时先准备 Python。每张必需卡片可独立标记，不能假定一定需要下载所有可选资源。
4. 下载中保留“此任务必需”的黄色标记，同时展示真实进度和阶段；下载完成仍在校验/安装时不能清除。资源经后端确认可用后清除该项高亮，显示就绪。
5. 暂停/失败时保留需求提醒，分别提供继续/重试；失败文案用明确错误样式，不能让黄色提示掩盖失败。
6. 返回原页再到资源页仍保留当前需求；只在本次需求满足或用户明确取消该任务引导时解除。离开页面、固定几秒计时、丢失键盘焦点都不是解除条件。
7. 就绪后显示“所需资源已就绪，返回新建任务/批处理继续”。不因为高亮消失而自动启动任务。
8. 自动定位只发生于一次明确操作及其导航序号，不在每次轮询或后台状态刷新时反复抢焦点。尊重关闭动效和系统减少动态效果，届时立即滚动，不强制 smooth。

实现边界：

- 复用后端现有 capability_requirements / _missing_batch_resources，不解析中文错误句子来猜资源 ID。
- 在 BridgeError 等现有协议上增加有类型、可选、兼容旧响应的资源 ID/依赖详情；经过原生白名单校验，再由前端定位。不能从任意字符串生成导航目标或执行路径。
- API 密钥和 Agent 登录是设置需求，不是“可下载资源”；二者采用同一套解释、定位、返回规则，但文案和操作必须区分。
- yt-dlp 对本地文件任务仍是可选项；“版本旧但仍可用”不等于缺失。说话人权重等按需模型沿用其现有获取流程，不能全局强制预下载。
- 保留已有下载体积确认、解释器选择等合法步骤；精确跳转本身不代表授权新下载。

## 3. UI 视觉与动效方向

### 3.1 统一令牌，渐进替换

现有基础并非空白：tokens.css 已有 160ms/240ms 和 ease-out，侧栏已有共享高亮，部分 Tabs 使用原生 View Transitions，并已有动画开关、系统减少动态效果及测试。

建议保留命名兼容，并补齐以下约定；数值是待体验验收的设计目标，不是已完成的性能结论。

| 用途 | 建议时长 | 缓动与幅度 |
| --- | --- | --- |
| 按下、焦点和即时状态 | 状态立即生效；形变 80–120ms | 不等待动画后再处理点击；按钮按下可缩至 0.98 |
| 悬停、小图标和选项背景 | 150–180ms | fluid；位置变化短且稳定 |
| 菜单、弹窗、轻量折叠 | 200–240ms | fluid；小控件可用克制的 spring |
| 完成通知的入场/离场 | 入场约 240ms，离场 160–200ms | 小幅位移加透明度，不遮挡主操作 |

参考曲线：fluid = cubic-bezier(0.22, 1, 0.36, 1)，spring = cubic-bezier(0.34, 1.3, 0.5, 1)。spring 仅用于滑块、选中指示等小元素，不用于大弹窗、整页或进度百分比。

不对所有 CSS 做一次性机械替换；先统一共享控件，验证后逐步消除散落的 180/220/460ms 与重复曲线。保留所有主题的颜色/字体，不引入额外装饰渐变。

### 3.2 按组件推进

| 区域 | 优化内容 | 必须保留的行为 |
| --- | --- | --- |
| 按钮、图标、下载控件 | 统一按下/悬停/忙碌状态，控件尺寸不因换图标跳动 | 禁用与忙碌有区别；操作立即生效；键盘焦点可见 |
| 自定义菜单、Tabs、侧栏 | 尽量复用已有共享高亮；选中与悬停分清；首次出现不从角落飞入 | 键盘导航、菜单可见范围和滚动；旧 WebView 无 View Transitions 时正常降级 |
| 弹窗和菜单 | 轻量透明度与缩放；关闭时先不可交互，再播放退场并移除 | 焦点限制、Escape、滚动锁、焦点恢复与遮罩都与生命周期一致，不能残留透明拦截层 |
| 高级设置、Agent 路径、日志折叠 | 优先复用现有 CSS grid 折叠；确有自适应需求再测量高度 | 收起内容不可获得焦点；不截断菜单；动画期间不逐帧读写布局 |
| Toast 和完成提醒 | 手动关闭、自动超时和替换都走一致退场；重要错误另有持久说明 | 动效关闭时也能清理；提供 animationend 与超时兜底，重复通知不堆积 |
| 任务/批次进度 | 阶段切换和真正完成时轻量反馈；条目状态稳定更新 | 不在每次轮询、每条日志、每次百分比变化时重新入场；不把视觉进度当完成依据 |

首轮不做全页面大范围滑动、不强制侧栏折叠、不增加鼠标跟随装饰，也不让菜单 hover 在大列表里为每项创建观察器。仅在真正需要共享高亮测量时使用受控 ref/一次性测量；已有 React activeIndex 足够时不引入 MutationObserver。

### 3.3 布局和可读性

- 右侧运行环境面板的状态图标、状态文案和操作位置一致，避免禁用的下载箭头看起来仍可下载。
- 资源/设置目标项增加“为什么来到这里”和“返回哪里继续”，把上下文直接放在目标卡片/字段旁，不靠用户猜测。
- 控件高度、间距、圆角沿用现有令牌；长英文错误、长路径、中英文切换和系统放大字体不挤掉主操作。
- 警告、失败、下载中、已就绪采用图标加文字，黄色高亮与键盘焦点样式分离；明暗及角色主题都要验证可读性。

## 4. 工程落点与顺序

以下为原定实施范围；具体完成情况见文末的实施记录。

### 第一步：状态与阻塞引导（先修功能，P1/P2）

- EnvironmentPanel + resources/state：修 BUG-UI-001，检查安装快照、轮询与重试的状态合并。
- BatchQueue + page/AppState：修 BUG-BATCH-001，将未提交草稿与错误引导提升到页面切换不会丢失的既有应用状态；避免重建任务。
- launcher/bridge + common/models + frontend types/bridge：补齐受控的缺失资源详情，保留旧错误响应兼容性。
- ResourceManager + Settings：实现 UX-RESOURCE-001 的精确锚点、需求高亮、具体原因与返回入口。
- 起始/恢复/追加入口共用规则，原生边界继续复核；不在前端复制上游整套路由判定。

### 第二步：统一基础控件（动效 P2）

整理 tokens/controls/dialog 与动画偏好，先覆盖按钮、菜单、Tabs。保留现有选中高亮，统一有限的进退场状态；只有多个组件确有重复需求时才提取小型共享辅助函数。

### 第三步：折叠与通知生命周期（动效 P2）

补齐 ConfirmDialog、CustomSelect、Toast 的关闭/替换/快速重开情况；再覆盖高级设置、Agent 路径和日志折叠。不增加通用动画框架。

### 第四步：回归、实机验收与发布决策

按下节矩阵验收，通过后再决定版本与发布方式。涉及原生 BridgeError 协议/桥接修改时必须重新评估完整更新包，不能预先承诺仅靠前端热替换就能兼容。

## 5. 验收矩阵与完成标准

### 功能自动化

- 资源状态：提交未返回、排队、运行未知总量、确定百分比、校验安装、暂停、失败重试、可用；模拟慢桥接和乱序/过期响应。
- 启动矩阵：新建/批处理/恢复/动态追加 × 本地文件/链接 × API/Agent/自动/手动路由；分别模拟缺资源、缺密钥、Agent 未就绪、路由失败与全部就绪。
- 精确定位：只缺 yt-dlp 不得定位到 Python；缺 API 不得跳资源；多项缺失能逐项处理；重复定位同一卡片仍能响应新操作。
- 草稿：去设置/资源再返回，批次链接、顺序、任务选项和并发不丢；纠正前置条件后只启动一次。
- 高亮：跨页面和轮询持续存在，仅资源真实可用/明确取消引导后清除；失败/暂停不误清；后台变化不抢焦点。
- 原生边界：旧响应、新可选字段、未知资源 ID、格式错误、缺少可选详情的降级行为均覆盖；原生校验不得被 UI 绕过。

### 浏览器与 Windows WebView 实测

- 中英文、明暗及两个浅色角色主题；最低支持窗口宽度、1080p/常见缩放和长路径/长错误。
- 鼠标与纯键盘；弹窗快速开关、菜单选择、路由切换、点击 Toast 关闭，均无透明遮罩残留、焦点丢失或重复事件。
- 动效开启、应用内关闭、系统减少动态效果三种情况；关闭状态仍看得出下载/安装进度，退场状态能正常清理，黄色提醒不闪动。
- 下载/任务/批次并行时页面仍可操作，不因每次轮询重启动画；长日志/长列表不做整体高度逐帧动画。
- 录制并检查普通 Windows 设备的交互及帧时间。以常见刷新率流畅为目标，不能把一次截图或 CSS 属性选择当成“保证 60fps”。动画优先 transform/opacity，不常驻大面积 blur/filter/will-change。

### 合并与发布门槛

1. 先补会失败的交互/状态测试，再实施修复；不能仅用正则断言“源码出现 LoaderCircle”证明交互正确。
2. 前后端相关测试、typecheck、静态构建通过，新增运行时问题可通过应用/任务日志定位；日志避免输出 API 密钥与带凭证的完整 URL。
3. 浏览器模拟与至少一次真实 Windows 组件下载/跨页返回验证通过。真实任务/账号调用若要额外费用，单独确认，不为动效验收偷偷消耗额度。
4. BUG-UI-001、BUG-BATCH-001 与 UX-RESOURCE-001 按文末所列范围验收；原用户环境的具体错误码与日志仍未取得。

## 6. 本轮分析的已知限制

规划时只做静态源码核对，没有原用户批处理错误码或日志，无法断言其唯一原因。实施验收使用隔离环境；未进行真实字幕识别、付费模型调用、打包后 Windows WebView 性能或逐帧测试。

## 7. 实施与验收记录（2026-11-04）
