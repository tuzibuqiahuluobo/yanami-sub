# 任务进度与模型来源选择（RC7.1）

## 现有架构

`TaskSettings.tsx` 已复用于新建任务和批处理，已有“自动 / API / 本地 Agent / 手动模型路由”四选一；不需要另造一套 `task_processor.py` 或第二份任务模型。`ProcessingView.tsx` 已有阶段列表，离开新建任务页有右下角任务进度球。FineSub 的 reporter 会给出真实阶段和部分 `completed/total`，但桌面 `WorkerReporter.progress` 当前丢弃了数字。

## RC7.1 方案

1. 保留一个来源选择控件和现有请求字段。文案明确：自动模式免费 Gemini API 优先；没有免费密钥才按可用本地 Agent 顺序尝试。显式 API、Agent、手动选择遵从用户选择，不暗自切换到另一类收费来源。检测到 CLI 仅是“可尝试”，不是“已认证”。
2. worker 继续使用 FineSub 的有序模型组回退，不加自定义 Agent 调度器。失败目标与原因来自 FineSub 的 route decision / execution attempts，逐项写入任务日志，避免只报“全部失败”。失败种类为永久配置错误时明确报错，不把磁盘等非 LLM 故障伪装成“纠错已跳过”。仅确认纠错翻译失败且已有本次原始字幕时才保留原稿并标记跳过。
3. `WorkerReporter` 把可信的 `completed/total` 作为节流的协议事件转发；UI 只在 `total>0` 时显示该阶段的数字和进度，否则保持不定进度球。不假设各阶段工作量相等，不显示无依据的总体百分比、ETA、token 或成本。
4. 任务页展示实际模型来源和候选顺序，明确这叫“尝试顺序”，而非“已使用模型”。如果上游工件有可信成功目标，可单独显示“实际使用”；否则只保留日志证据，不从候选组猜测成功 Agent。ASR、分离、稳定化标为本地处理，不能误称由 Agent 完成。
5. 状态恢复从已有 `JobSnapshot.events` 还原阶段数字，完成/失败/取消时清除运行中进度。右下角进度球继续与任务页使用同一状态；中英两套文本一致，避免中文被硬编码到英文 UI。

## 验收

- 新建任务和批处理保存同一来源选择；免费 API 存在时自动模式不因为无健康 Agent 提前失败；免费 API 缺失时才检查 Agent。
- reporter 的 0/未知、已知总数、重复回退、重启恢复及不同页面的进度提示均有测试；无总数时绝不显示伪造百分比。
- Agent 连续失败能看到每个候选的真实错误并继续下一项；所有候选耗尽时只对允许的纠错失败作原稿兜底，阶段显示叉号。
- 不通过 `--version` 检测或静态目录推断订阅额度、真实模型响应、实际 token 花费。
