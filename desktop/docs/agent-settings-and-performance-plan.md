## 当前版本更新公告

建议在“说明文档”右侧增加“本版更新”入口，打开可滚动对话框；窄窗口上下排列。
内容应在构建时随版本打包，来源为同版本发布说明，显示安装版本号和发布日期。未找到匹配说明时明确提示缺失，并允许打开该版本 Release 页面。
不要显示未发布内容、用最近一次更新检查结果冒充本版内容，或将远程 Markdown 当 HTML 执行。
应复用现有更新公告展示组件，统一长文本换行和按钮布局。

## 路径选择与音效 UI

路径卡片保留折叠列表、自动检测填入和保存/清除动作；路径展示改为只读，增加“选择 CLI 文件”“选择安装目录”。
原生选择器复用 pywebview 的有效文件筛选格式，选中后调用既有安全校验，不执行所选程序，不扩大磁盘扫描，不允许 shell shim 绕过校验。
取消、错误和打开选择器期间都有明确状态；错误展示在对应 Agent 卡片中。

音效沿用现有主题变量和原生表单行为，不新增组件库。
主开关关闭时保留各事件选择，只禁用事件开关；音量仍可调整，明确点击试听仍可测试声音。
开关支持键盘/焦点与可访问名称，音量范围 0–100，提示音默认开启、50%，仅影响本应用。

## 本地 Agent 就绪应该验证到什么程度

基础检测继续默认不请求模型：路径、可执行性、CLI 版本和本地声明能力。
当前 `ready` 只代表 CLI 基础检测通过，设置页改称“CLI 就绪”。

账号检测需要按工具分别实现，不能通用地读取某个令牌文件就判定登录有效：

1. 工具有稳定的只读登录状态命令时，用户点击检测后读取结果，不导出凭证；离线结果注明“本机登录记录，服务端尚未验证”。
2. 模型权限只认账号/区域的权威模型列表；CLI 帮助中的候选模型不等于账号有权限。没有可靠接口时显示“未验证”。
3. 额度按模型/额度池显示来源与检查时间。无法读取余额时显示“未知”，不要用一次调用成功推算还剩多少额度。
4. 单独提供“测试所选模型”：先展示模型、是否可能收费、网络请求与额度消耗；用户确认后发起最小请求。不能默认遍历所有 Agent/模型。
5. 真实任务中的认证、模型权限、额度和临时网络错误分别记入日志；认证或无权限错误不要重复空转，应提示修复/切换。批处理共用相同检查规则。

## WorkBuddy 重点结论

来源：用户上传的 `agent.md` 与 [上游 Agent 手册](https://github.com/caca2331/finesub/blob/main/docs/manual/agent.md)。最新手册和本项目固定内核不能视为同一个版本。

- FineSub 使用 WorkBuddy 桌面端携带的 CodeBuddy CLI 并复用其登录。认证错误优先打开官方桌面客户端重新登录，不由本应用收集或搬运凭证。
- WorkBuddy 是纯文本 Agent。音视频佐证不可用，不代表纯文本纠错/翻译不可用；联网检索与音视频能力须分别显示。
- 可用模型由账号/区域服务端权限决定，不是只看 CLI 版本；`--model` 被拒绝不能一概当作登录过期。
- 上游说明 GLM/DeepSeek 的高思考档可能不收敛，低思考档可减少此类长等待。这是优先排查方向，不是本次 18 分钟任务的已确认根因。
- 本项目固定 v0.5.1 目录中，GLM/DeepSeek 的思考映射为 `high,low,low`；默认路由 research/knowledge 在 quality 档请求 high。纠错组缺省 medium，不能笼统称全部纠错都是 high。
- 当前内核的执行设置默认 Agent 超时为 1680 秒（28 分钟）。若一个调用超时再重试，总时间可能接近一小时；需查看实际调用记录确认次数和实际覆盖设置。
- 当前自动 Agent 路由从 `workbuddy-capable` 选择候选，包含 HY4 和 DeepSeek/GLM，并非按用户账号实时授权列表生成。
- 不同 WorkBuddy 模型有不同额度池。HY3/HY4 的目录配置有 `hy3-x`/`hy4-preview-x` fallback，可能从免费额度切到收费；GLM/DeepSeek 也不能当免费模型使用。检测与提速都不能偷偷触发收费。

当前 RC7.7 已有 WorkBuddy 认证分类兼容修复与官方客户端登录入口；本次不重复实现或升级整个上游。

## 性能排查与提速顺序

需要该任务的 `task-log.txt` 和所选 Agent/模型。优先读取已有阶段时间、resource usage 与 `agent-sessions.jsonl`/具体调用日志，避免增加重复的昂贵请求。

1. 分开统计：媒体准备、人声分离、ASR、字幕稳定化、调查/规划、纠错翻译、知识库写回、导出；不能把总时长全部算成 ASR。
2. 模型慢：区分初始化、生成、工具回合、超时重试、账号限速。若证实 WorkBuddy research/knowledge 高思考空转，可提供明确的“快速/质量”选项，按模型调整私有任务设置，而不是降低所有 Agent 思考档。
3. 无权限/未登录：立即给出可操作提示；同账号已经确认的错误不应在所有模型和批处理任务中反复等待。
4. 本地计算慢：分别确认 PyTorch、人声分离 ONNX 和 CTranslate2/Whisper 实际设备。ONNX CPU 警告不能证明 Whisper 也在 CPU；根据 GPU/显存选择合适批次，避免显存溢出和 CPU 回退。
5. 缓存与恢复：保留有效 ASR、稳定化和纠错检查点；重试不重做已成功阶段。
6. 并发最后调整：先解决重复调用和空转，再评估窗口并行；不要无依据提高并发，引发限流、上下文质量变化或付费调用增多。

## 收到任务日志后的核对结果

用户提供 `task-log (5).txt`（156 行）后，以上“等待日志”已解除。
本次从 15:50:43.812 到 17:09:45.477，约 **79 分 2 秒**；成功生成并保存了最终字幕，不是任务失败。

| 流程/模型调用 | 耗时 | 证据 |
| --- | --- | --- |
| 人声分离 | 117.636 秒 | `stage=vocal_separation` |
| ASR | 59.336 秒 | `stage=asr`，该阶段 GPU 峰值 1.52 GB |
| 稳定化/原始字幕导出 | 0.112 秒 | 两项 stage timing 总和 |
| LLM 完整流程 | 4563.847 秒，约 76 分 4 秒 | `stage=llm_harness`，占总时长约 96% |
| 其中调查/搜索调用 | 1856.684 秒，8 次 | research 2 次 + search_judge 6 次 |
| 其中规划调用 | 728.842 秒，3 次 | planning-text |
| 其中纠错调用 | 1757.889 秒，2 次 | correction-text，两窗口串行 |
| 其中知识库更新调用 | 113.843 秒，1 次 | knowledge |

模型调用小计 4457.258 秒，剩余 LLM 时间包括搜索请求、工具协议与其它框架开销。

具体结论：

- 主要慢调用是 `hy4-preview`，不是 GLM/DeepSeek 的高思考问题已被确认。本次 DeepSeek Pro 仅有一次约 90 秒的 search_judge 调用。
- 三次 `ended without a submit; retrying once` 分别发生于搜索评判两次、规划一次。CLI 退出码 0 不等于 MCP 任务提交成功。不要绕过提交/校验协议把无效输出当成功；进一步修驱动需对应 capsule 的事件与任务记录。
- 本次没有 timeout 或认证失败的日志，不能归因于 28 分钟超时、登录过期或 5070 不识别。多个 HY4 调用和最终任务均成功。
- 三轮检索全部 `extracts=0`，实际搜索质量/抓取为何为空需要检索明细；不能直接认定没有结果、没配搜索 Key 或网络被阻断。减少此流程是有依据的提速方向。
- ONNX CUDA 警告属于 separator；ASR 总时长不足一分钟，且阶段 GPU 峰值非零，不支持“识别是主要慢点”的判断。日志未直接声明每个推理算子的设备，不据此保证全部算子都在 GPU。
- 最后的 `local-workbuddy-hy4 未能使用（unavailable）` 是路由历史中部分调用失败的诊断汇总，与最终成功并不矛盾，不应解释成整个账号都不能用。
- 重复日文音节/词属于 ASR 重复与幻觉处理，不是中文/日文日志编码损坏；该项异常恢复约 4.23 秒，不是近一小时的原因。

### 本次新增的可选提速入口

在共享的任务设置组件里，明确选择 WorkBuddy 或 WorkBuddy 手动路由后，提供“应用快速设置”。新建任务和批处理共用此入口。
用户主动点击后将媒体设置为 text，difficulty 设置为 efficiency，retrieval/knowledge 设置为 none；`fast=auto` 继续保留预算检查，不强制把长视频塞进单窗口。
这是 FineSub 已有的合法配置组合，可减少联网调查、搜索评判和知识库处理；仍保留纠错翻译，可能减少背景/术语校验。
不改选定模型/路由/Agent，不提高并发，不修改账号、GPU 或全局思考档，不触发模型测试，也不为现有正在运行的任务更改设置。
HY4 在当前目录的三档思考均映射 high，所以仅切换 efficiency 不能声称 HY4 会自动使用 low；提速依据是减少额外流程，而非虚构模型低思考支持。

尚未用真实 WorkBuddy 模型重跑比较，因此不能宣称耗时已经降到某个数值。

## 追加修复：反馈页使用默认浏览器

主按钮此前默认创建第二个 pywebview GitHub 窗口，只有“在浏览器继续”才打开外部浏览器。
已移除创建内嵌窗口、限制其导航和绑定主窗口关闭回调的分支，统一复用系统默认浏览器；登录、截图/视频附件选择和最终 Issue 提交都在 GitHub 网页完成。
前端只保留一个“新建 GitHub Issue”入口并注明打开方式。旧客户端传入 `browser=false` 时也不再创建应用窗口；新前端默认明确发送 `true`，兼容旧后端的浏览器入口。
草稿、完整描述复制、摘要预填和本地诊断包不变。浏览器返回打开失败时显示设置/重试提示，不报假成功；异常由现有桥接日志和页面错误提示处理。

本轮后端 87 项通过、1 项符号链接权限测试跳过；全部前端 118 项通过，类型检查和生产静态编译通过。未执行真实登录/提交，也未发布或推送。
