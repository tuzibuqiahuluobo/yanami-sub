# FineSub 0.6.0 分阶段迁移

状态：前八个检查点完成，本地 0.6.0 候选已通过原生编译/启动烟测；尚未发布、安装覆盖或完成真实模型验收。工作分支 `codex/finesub-060-migration`，以 `v0.1.3-rc.1` 为基线。

## 第一阶段：升级前防护与启动配置兼容

已实现：

- 进入知识库读写、精修回灌或单个/批量任务中需要知识/风格的 LLM 管线、ASR 知识上下文前，检查已有 SQLite 的 schema。明确关闭这些能力的任务不打开知识库。
- 相同 schema 不升级、不产生备份；较新 schema 拒绝以旧内核继续打开，提示使用新版或离线恢复备份。
- 需要升级时，先在核心知识库写锁下用 SQLite backup API 复制一个一致的快照，包含已提交的 WAL 内容；核对版本与 quick_check、落盘完成后才调用核心自己的迁移。
- 备份位于知识库同级的 `knowledge-backups/`，名称包含原 schema、目标 schema、UTC 时间和唯一编号。备份失败则不迁移，迁移失败保留备份，不自动覆盖恢复。第四阶段已扩展为完整迁移数据目录，见下。
- 同进程并发入口串行进行迁移前检查，跨进程沿用核心写锁。备份操作设有时间上限，失败不会留下被误认为有效备份的临时文件。
- 设置读取优先使用 0.6.0 的标量注册表；保留 0.5.1 入口，未配置的值仍是“跟随默认”，不把核心默认值写进配置文件。
- 0.6.0 不再导入/应用旧 WorkBuddy 鉴权补丁，不覆盖其原生 CodeBuddy 实现；旧核心仍使用原补丁。

第一阶段最初只提供数据库快照；第四阶段已补齐原文件/配置备份与离线恢复副本校验。它仍不是整个应用数据的一键回滚产品，也不自动切换恢复点。不要在应用或任务运行时直接覆盖 knowledge.sqlite。

## 第二阶段：运行接口、历史记录与独立 CodeBuddy

已实现：

- 单任务、批处理与静态 manifest 共用参数边界：在 0.6.0 下只传单一 `llm_media`，取原纠错媒体覆盖值或原统一值；旧规划媒体仅为读取旧记录保留，不传给新内核。0.5.1 仍按原双媒体接口调用。
- 启动前的 profile 与原生检索能力校验也匹配两代签名，不再向 0.6.0 传入已删除的 `planning_media` / `fast_enabled`。
- `collect` 仅作为旧输入别名接受，任务、偏好和界面统一使用 `read`；调用/导出给 0.5.1 时才转回 `collect`。新增任务默认值仍保持原有显式选择，不擅自启用新预设、并发或快速流程。
- 历史任务和历史批次不再因当前模型目录已删除某个 target 而消失。归档读取仍检查结构，但不要求旧模型今天仍存在；重试/继续前重新执行当前模型校验，不能借归档读取绕过执行限制。
- 旧 `planning-*` / `search_judge` 模型绑定和 WorkBuddy 桌面通道不能可靠地一对一转换成新路线：保留历史，重新执行时明确要求重选，不把它们自动改绑到 `research`、其他模型或独立 CodeBuddy。
- 0.6.0 的 CodeBuddy 使用 `LOCAL_CODEBUDDY`；支持原生可执行文件及官方 npm 包 `@tencent-ai/codebuddy-code` 的 `bin/codebuddy` 入口，读取包身份校验。检测不再扫描 WorkBuddy 桌面内置 CLI/Node，也不读取旧桌面凭据。旧保存路径原样保留，但不会当成新通道路径自动执行。
- 前端按后端明确报告的接口能力显示独立 CodeBuddy、登录说明和统一媒体控件；坏的自定义预设不会让前端误判核心接口。登录按钮只在用户点击时打开选中 CLI 的交互窗口，无 shell 拼接、不复制凭据。自动检测和任务辅助进程仍隐藏窗口。
- 就绪检测只验证 CLI/版本/接口能力，不声称已登录、有模型权限或额度。中国站/国际站需在官方 CLI 中选择并登录；继承对应站点环境，不为检测发送模型请求。
- 上游 `codebuddy-capable` 含可能扣积分的候选，只有明确指定 CodeBuddy 或手动选其模型路线才会使用；原有“按顺序尝试所有 Agent”不会因发现这个新 CLI 自动启用它。界面与无候选日志给出原因及重选入口。
- 审计发现批处理调用的是核心构建的阶段闭包，并不经过桌面单任务执行函数；已在构建批次任务前调用共享的知识库 schema 防护，补齐第一阶段的漏接入口。

此阶段没有修改用户自己的 `config.toml` 预设或模型目录。旧自定义预设、已删除的模型、`planning-*` 绑定与新预设默认值仍需下一阶段备份后审查；不承诺任意旧配置直接切换 0.6.0 即可运行。

## 第三阶段：冻结精修回灌与中文路径初始化

已实现：

- 自动风格沿用原任务记录的选择及其版本，核心 research context 优先于复制的 artifact；不因用户后来编辑风格目录就重新抽选。写入资格仍由核心按当前目录检查，已停用的风格不改写，也不自动替换成其他风格。
- 开启成功后清理中间产物时，单任务/批处理共用入口，在移除 LLM 会话目录前原子保留一份轻量 `*-style-selection.json`。精修回灌在核心原始记录缺失时才读它；保存失败则保留原目录并记录警告，不让已发布字幕的任务失败。旧 0.5.1 不走这个新记录接口。
- 生成提案前后用核心材料构建器核对原轴、译轴、精修轴及任务上下文的语义指纹；生成中材料有变化就要求重新生成。模型的文本、句柄绑定、读取版本和对应窗口材料一起保存在本地草稿，不把原始 CSV/句柄表塞进前端响应。
- 点击应用只处理同一份冻结提案：调用核心自己的精修对齐证据和风格标记校验/记账，不重读后来改过的 SRT，不再请求模型。保留版本冲突检查、原任务标识及重复记账保护；核心提交后桌面回执中断也可恢复。
- 风格写入限定于本任务选中的条目，其他窗口时间点或未渲染句柄的标记交给核心拒绝。证据存储异常仅产生警告，不把已经提交的知识变更伪装成失败。
- 没有条目变更但存在有效反馈证据时，允许应用，并准确显示“仅记录反馈证据”，不再把它当作新增知识条目成功。
- 单任务、批处理、知识库三个独立 worker 启动时调用 0.6.0 自带的 UTF-8 CRT 路径初始化，补齐桌面绕过核心 CLI 入口的差异；0.5.1 无该接口时保持原行为，不修改 GUI 进程的全局区域设置。

这里使用固定 0.6.0 源码的风格记录辅助接口；后续更换上游版本时需要重新核对。没有对任意旧自定义配置做推测性改绑，也没有实现运行环境自动重建。

## 第四阶段：完整迁移数据快照与非覆盖式恢复

已实现：

- schema 升级前，在原有核心写锁和进程内迁移门下建立一个自包含快照目录。数据库继续使用 SQLite online backup，包含已提交的 WAL 内容；不直接复制活跃的 WAL/SHM/journal 作为恢复数据库。
- 按原始字节保留知识库内的常规文件、隐藏文件和空目录，包括尚未收录的 `rendered/` 人工编辑、`.manifest.json`、共享记录等；同时备份同级 `knowledge-proposals/` 待应用提案及实际存在的原 `config.toml` / `model_catalog.psv`。不调用核心打开/刷新知识库来“整理”这些文件。
- 单任务和批处理在生成任务私有路由配置前捕获原配置路径，再传给共享防护入口；不会把临时生成的模型组配置误当成用户原配置。知识库 worker 仍在自己的路由覆盖前备份。
- 每个文件有大小与 SHA-256 清单；完整核对文件列表、路径、数据库版本和 quick_check 后才发布备份、执行核心迁移。复制期间检测到文件内容、时间戳或清单变化就中止；不悄悄略过无法读取的目录，也不跟随子目录中的符号链接/Windows 联接点。
- 目录已有历史文件却缺少 `knowledge.sqlite` 时停止自动初始化，保留原文件并要求离线核查/导入，避免绕过备份开始一次旧文本导入。空目录和全新用户不额外备份。
- 提供仅依赖标准库的校验及恢复副本工具，即使目标核心不能导入，也能核对/复制备份。恢复目标必须是新目录，不能位于原知识库或快照内部；现有目录和悬空联接点不会被覆盖或跟随创建。

在包含桌面源码的目录中运行，使用本机可用的 Python：

```powershell
python -m desktop.backend.knowledge.backup verify "<快照目录>"
python -m desktop.backend.knowledge.backup restore "<快照目录>" --to "<尚不存在的恢复目录>"
```

恢复目录中包含 `knowledge/`、`knowledge-proposals/`（原来存在时）、`config/`（原来存在时）和校验清单。工具只生成并验证副本，不修改实际使用位置，不执行新 schema 迁移或渲染收割。复制中断会保留新的不完整目录供排查；再次使用前必须通过 verify，重试请另选新目录。

快照可能包含私人知识、共享凭据及配置；本工具不加密，也不把它纳入反馈包或上传。校验和用于检测损坏，不是来源签名。它不备份整个应用、运行环境、模型/下载缓存、任务媒体/历史或独立 `.env`，因为本次 schema 迁移不修改这些数据；不能将其宣传为整机/账户迁移备份。实际回滚的交互、旧文本库导入和恢复点启用仍是后续发布闸门。

## 第五阶段：配置迁移审查与运行环境启动前核对

已实现：

- 启动 LLM 任务时先进行只读配置审查：旧 `planning_media/correction_media` 要求明确迁移到统一媒体语义，再由核心自己的模型目录/预设/绑定校验器检查配置。不会删除用户注释、自动改绑已移除模型或将 WorkBuddy 凭据转给 CodeBuddy；纯识别任务不受这道 LLM 配置预检拦截。
- 资源检查与设置面板共用配置路径解析，包含显式自定义文件名、checkout 和用户数据目录回退。运行环境策略沿用核心 `RuntimeSettings` 默认值与合法值；无效 TOML/策略拒绝自动修复，而不是忽略用户写下的关闭设置。
- 仅在任务启动/继续或用户手动诊断时运行新核心的 `condition/check`；资源轮询只展示缓存结果，不触发安装、哈希或新解释器探测。已发现与依赖锁不一致的运行环境显示为需修复，不能借“过期工具仍可用”的通用规则继续启动。
- `integrity_check=off` 不自动做逐文件核对，手动诊断仍可核对；`on` 每次检查，`auto` 复用核心成功标记规则。单任务成功、批次全部项目成功后才写标记，使用桌面应用版本作为此调用方的版本身份；标记写入失败只警告，不把已完成字幕变成失败。
- 前端、桥接和后台安装队列区分自动安装与用户手动点击。自动修复遵守 `auto_repair=false`，队列真正执行时再次读配置；首次安装不被误当成替换。手动修复可以覆盖自动策略，但不能绕过正在使用的租约。
- 已知损坏/过期/锁不匹配的环境沿用核心 staging 重建和换入流程，并要求新环境哈希核对；日志先说明核对结果及能识别的额外包移除清单。任务、知识库和模型缓存不在运行环境重建目标内。
- 补齐批处理父进程交接租约，以及知识库/模型预下载父子进程租约。子进程导入运行环境之前就有父进程保护；子进程自己的租约在父进程退出时仍有效。批次创建失败、管道失败或 reader 结束时释放/收尾相应交接资源。
- 新检查/强制安装关键字只接入拥有这些 API 的核心；0.5.1 继续使用原安装接口。开发者指定的非托管解释器不被自动重建。

第五阶段只实现审查，不修改配置；第六阶段已补齐范围受限的确认式媒体转换，见下。新增 check 是文件/依赖锁核对，既有手动诊断仍保留 import 探测；没有在本机运行真实环境重建来证明 GPU 栈可用。

## 第六阶段：任务失败后核对与确认式媒体配置转换

已实现：

- 单任务失败、worker 意外退出、批次失败或部分项目失败后，在现有 reader 中进行一次只读环境核对。它不会因以前的成功标记而漏检，仍尊重 `integrity_check=off`；取消、成功及过期进程不触发。旧核心和非托管开发解释器保持原行为。
- 检查放在管理器锁之外，原任务错误、状态和已发布输出保持不变；只向当前任务日志附加核对结论。检查本身失败也不覆盖原错误。不会在失败处理里自动重装、重跑任务或消耗模型额度；发现问题后由用户到资源页处理。
- reader 的进程身份校验覆盖相同批次 ID 的继续/重试场景，旧 reader 不能改写新进程的状态、清空其引用或写入检查结论；自己的交接租约在检查和日志收尾后释放。
- 设置页新增媒体配置转换入口，沿用现有界面和确认弹窗。预览只读，展示配置位置、拟更改和阻断原因，不返回原始配置、密钥或模型目录正文；应用每次都必须明确确认，不提供“下次不再询问”。
- 只将明确、有效且不冲突的 `correction_media` 转为 `media`，并移除已删除的 `planning_media`。仅有规划媒体、媒体冲突、难以安全定位的 TOML 写法、复杂多行/数组配置和失效模型路线均要求人工审阅。原模型绑定、自定义模型清单、凭据及预设不被猜测性改写。
- 使用已有配置编辑器的定位规则保留中日文注释、引号和换行；候选内容必须通过核心自己的目录/路由校验。预览令牌同时绑定原配置、自定义模型清单及候选内容；应用时在配置锁下重新读取，预览过期就拒绝。
- 写入前，在原配置同级 `config-backups/media-v1-<UTC>-<唯一编号>/` 保留原配置及存在的自定义模型清单，逐文件核对 SHA-256 并发布备份清单，随后再次检查源文件才原子写入。备份失败不会改原配置；外部编辑发生变化时不覆盖，并保留已完成的备份供核查。
- 应用由核心活动屏障阻止与任务、知识库操作及模型预下载并行。写入成功但界面/worker 环境刷新失败时，准确报告“已更新，请重启”，不误报成写入失败。备份包含私人配置，不加密、不上传；这是独立的媒体转换回执格式，不能用知识库快照恢复工具直接恢复它。

本轮只在临时目录测试转换，没有改动实际用户配置，也没有运行真实环境重建或原生交互验收。

## 第七阶段：固定源码与依赖/构建链同步

已实现：

- 本地候选依赖改为 `finesub==0.6.0`，唯一源码身份描述在 `desktop/resources/core-source.json`：版本、上游仓库、tag 和完整提交。CI 与手动 Windows 构建都按该 SHA checkout，安装开发依赖之前再次验证；不会跟随 tag/main 移动。
- 本地开发安装、PyInstaller 和源代码打包共用源码验证器：要求核心 tracked source 干净，VERSION/提交匹配描述文件与 pyproject，并包含受 git 跟踪的运行时清单、模型清单、下载源与两份依赖锁。缺失/改动/错配直接拒绝，不以忽略完整性校验的方式继续构建。
- 冻结启动器与最终版本目录共用 tracked 文件列表。未跟踪的 Python 草稿、日志、缓存与测试不进入冻结包；核心源码继续独立于桌面代码，不复制一份下游 GPU 依赖解析结果。
- `app-manifest.json` 在原有桌面 sourceCommit、逐文件摘要基础上增加 coreVersion/coreCommit。安装器和复用 `-SkipBootstrap` 的更新包构建会核对核心身份与锁/清单摘要，拒绝误用旧核心产物。
- `setup-dev.ps1` 增加显式上游源码路径（或 `FINESUB_UPSTREAM_SOURCE`），先验证再安装；读取该核心的 canonical lock，保留桌面已验证的 uv 0.12.17 下载恢复覆盖，与启动器用测试保持一致。`-DesktopOnly` 跳过大型运行依赖，但仍安装/验证选定核心；脚本不在应用启动时自动运行。
- 版本目录补齐应用自己的 `VERSION` 并纳入摘要清单，使核心启动前核对与 worker 的成功标记使用一致的桌面版本身份；不把核心 0.6.0 与桌面应用版本混写。
- GitHub 构建继续只手动触发、只提供下载产物，不自动提交/创建 Release。没有改动应用 VERSION、更新频道、信任公钥、签名流程或线上配置，也没有触发云端构建。

固定锁中的 Windows CT2 已更新为 `4.8.1+finesub0.6.0.cu128`，与 torch 2.11/cu128、torchaudio、torchvision、triton 的整组约束一起使用。已对照上游 [发布资产](https://github.com/caca2331/finesub/releases/tag/ct2-4.8.1%2Bfinesub0.6.0) 元数据核对其文件名与 SHA-256（`7567ef160cccea178c4b0accdb18ff35812b7a198b60419208ce8567b392c63b`）；没有下载二进制或声称验证了实际 DLL。锁变化会重建既有托管环境，需通过实际安装/修复和 CPU/GPU 解码验收才能发布；不能拿单元测试替代它。
